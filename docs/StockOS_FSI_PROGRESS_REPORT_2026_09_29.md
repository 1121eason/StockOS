## 4. 73 個拒收到底代表什麼

全量重算涵蓋 232 個歷史候選：

| 原結果 → 新 G 結果 | 數量 |
|---|---:|
| 原 accepted → 仍 accepted | 98 |
| 原 accepted → 改為 rejected | 73 |
| 原 rejected → 仍 rejected | 61 |

73 個變動包含原本的 16 個空支持案例，因此另外受影響的是 **57 個**。其中 72 個因支持／反證角色重疊被拒，1 個因方向不受支持被拒。

這代表 G 更嚴格地執行證據規則；仍需讀原文，確認是否有模型把證據角色放錯、但本來有合理內容的結論被擋下。不能直接說「消除了 73 個錯誤」，也不能把拒收增加當成 FSI 品質改善。

35 張卡是原 M4.1 的人工審查單位；73 個是 G 造成的結論變動，兩者粒度與範圍不同。它們可能對應同一批來源或部分結果，**不能相加成 108 項完成分母，也不能互相替代**。

| 3：S1 通過後 | 準備 S2 的實際執行條件 | 工程模型＋Owner | live adapter 的工程驗證、固定 source／cutoff／設定、呼叫與重試上限、模型身分限制與評估方法明確；取得 S2 範圍批准 |

| 5：有品質證據後 | 決定採用及候選正式升格 | Owner＋工程模型 | 根據結果決定採用、修改或暫不採用；正式套用、資料遷移影響與驗收另行處理 |

SQLite 與 PostgreSQL 分開列狀態：若 SQLite 的兩項缺口已修復並通過驗收，可以確認 SQLite 層級的工程完成；沒有 PostgreSQL 證據時仍不能宣稱跨資料庫完成。

B 是「相同基本證據規則 G＋證據角色澄清」；C 是「B 再加入 FSI 研究方法」。比較目的是判斷 FSI 的額外方法是否改善結果，不預設 C 一定勝出，也不把 G 修補本身的效益算給 FSI。

## 6. M4.1 結案與 FSI 實驗是兩條驗收線

- **既有 M4.1 結案線：** 原 35 張卡的真人判定、Q2／Q3 語義差異解釋、適用版本的資料庫／回歸證據與其他原定門檻。歷史機械 PASS 不能代替它們。
- **FSI 候選線：** S1 補修與工程驗收 → S2 條件與批准 → 真實 B／C 比較 → 決定是否採用並正式升格。

FSI 尚未升格；S1 或 S2 通過也不能自動把 M4.1 改成 Final Pass。M4.1 的真人審查可以先推進，不必等待新的 B／C 結果。
